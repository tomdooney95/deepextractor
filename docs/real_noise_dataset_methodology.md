# Real O3/O4 Noise Dataset: Methodology

This document records the design decisions behind the O3 and O4 real-noise
separation training datasets, generated by `scripts/generate_real_separation_data.py`.
It exists to explain *why* the pipeline works the way it does, not just what
the code does line by line — for that, see the script's own docstrings.

## Motivation

The existing separation training pipeline (`generate_separation_data.py`)
uses simulated Gaussian noise, colored by bilby's own analytic PSD. This
dataset instead uses **real O3/O4 detector noise**, fetched and whitened on
CIT (`get_clean_backgrounds.py`), so the network trains against real
detector characteristics (real spectral lines, real non-stationarity, real
residual non-Gaussianity) rather than an idealized analytic approximation.

## Real noise and PSD matching

Real noise segments were whitened per-context using GWpy's `.whiten()`
(FIR inverse-spectrum-truncation), against a PSD estimated from that
specific 36s context — not a shared analytic curve. For the earliest
fetched backgrounds, the PSD used wasn't saved at generation time; it was
recovered afterward by `get_segment_psds.py`, refetching the same context
and recomputing the PSD with identical parameters (`fftlength=4,
overlap=2, method='median', window='hann'`) to exactly reproduce what
`.whiten()` used internally.

**Bug found and fixed during this process**: both `get_clean_backgrounds.py`
and `get_segment_psds.py` originally saved PSDs as `float32`. Real strain
PSD values in the sensitive band (~1e-46 to 1e-48) are below float32's
smallest representable magnitude (~1.4e-45) — casting silently flushed
~99.9% of PSD bins to exact zero. Verified independently against bilby's
own published aLIGO design curve, not just against this pipeline's own
output. Fixed by switching PSD storage to `float64` (whitened noise
*samples*, which are O(1) magnitude, were never affected and stay
`float32`). The original backfill run had to be regenerated from scratch
after this fix, since `get_segment_psds.py`'s resume/checkpoint logic
treats "has an entry" as "already done," corrupted or not.

When an astrophysical signal is injected into a real-noise sample, it is
generated as a colored bilby waveform and explicitly whitened via GWpy's
own `.whiten(asd=...)` against that specific sample's matched real PSD —
not bilby's `whitened_time_domain_strain` (a different algorithm: bilby
does a direct per-bin frequency-domain division by the ASD, GWpy applies a
finite time-domain FIR filter approximating the same operation). Mixing
the two would make the injected signal and the real noise it's summed
with inconsistent with each other.

## H1/L1 pooling

Real noise availability is wildly asymmetric between detectors and
between sub-runs. Counting actual 8s samples in `backgrounds_<RUN>.pkl`:

| | H1 | L1 |
|---|---|---|
| O3a | 9,191 | 546 |
| O3b | 2,939 | 975 |
| O4a | 12,025 | 281 |
| O4b | 8,457 | 34,781 |

Pooled per run: O3 H1=12,130 / L1=1,521 (8x apart); O4 H1=20,482 /
L1=35,062 (roughly comparable, O4b's L1 abundance compensates O4a's
scarcity). Rather than let L1 (for O3 especially) be starved of unique
noise relative to H1, **H1 and L1 samples are pooled into one shared draw
pool per run**. A generated sample's two detector "slots" each draw
independently from this shared pool, regardless of which physical
detector the noise segment originally came from — the matched PSD for
each drawn segment travels with it, so a slot filled with L1-origin noise
is still whitened against L1's own matched ASD, not H1's.

This deliberately breaks the property that "the H1 channel always
contains real H1 noise" during training. Real noise is close to
statistically comparable between H1 and L1 once whitened against its own
matched PSD, so the cost of this is judged to be small; the benefit is
that the smaller detector's data no longer caps the dataset's usable
scale.

## Samples vs. contexts

`get_clean_backgrounds.py` slides a 2s step across each 36s context's
32s usable (edge-cropped) region, producing 13 overlapping 8s samples
per context. Adjacent samples in that set of 13 share 6 of their 8
seconds — they are not independent draws, just shifted views of the same
underlying noise realization. The "pooled sample" counts above therefore
overstate true independent diversity by roughly 13x:

| | pooled samples | ÷13 ≈ independent contexts |
|---|---|---|
| O3 (H1+L1) | 13,651 | ~1,050 |
| O4 (H1+L1) | 55,544 | ~4,273 |

This matters for interpreting how aggressive the eventual duplication
factor really is (see below), and for the train/val/test split: since
`gps_starts` is a per-*context* value (all 13 samples from one context
share the same value), splitting by unique GPS time automatically keeps
an entire context's correlated samples together in the same split — no
extra bookkeeping needed to avoid leaking correlated content across the
train/val/test boundary.

## Train / validation / test split

Three-way split, by unique context (i.e. by unique `gps_starts`), not by
individual sample:

- **Train (80%)** and **validation (10%)**: stratified by time block
  (contexts binned by GPS time into consecutive blocks, e.g. weekly;
  within each block, contexts randomly assigned train or val in that
  ratio) across the **first 90%** of each run's GPS range. This gives
  both sets representative coverage of the whole run's noise
  characteristics, and keeps validation loss a clean signal for early
  stopping / LR scheduling — uncontaminated by any real detector-state
  drift between "early" and "late" in the run.
- **Test (10%)**: the **chronologically last 10%** of each run's GPS
  range, held out entirely — never touched by training, early stopping,
  or LR scheduling. Evaluated exactly once, after training is finished,
  specifically to test forward generalization: does a model trained on
  the first 90% of an observing run generalize to whatever the last 10%
  turned out to look like, including any real detector drift across that
  boundary? Unlike validation, this set is *supposed* to be sensitive to
  such drift — that sensitivity is the point of keeping it separate from
  validation rather than a flaw to control for.

## Sliding window at generation time

Within a single already-extracted 8s sample, the full 8s is already
edge-crop-clean (cropping was applied once, at the 36s-context level,
before the 8s samples were sliced out). The final training example only
needs 4s, so there is up to 4s of slack in where that 4s window starts.
Rather than always taking the same fixed middle 4s (which discards half
of every fetched clean sample and makes every reuse of a given sample
byte-identical), each duplication draw picks a **random start offset**
within that 4s of slack. This adds real (if autocorrelated) variation to
repeated draws of the same underlying sample, at zero additional cost —
no new fetching or PSD backfilling required.

## Noise augmentation: sign flip and time reversal

Applied to the real noise component only, before signal/glitch injection
— never to the signal or glitch themselves.

- **Sign flip** (negate amplitude): applied across all three splits
  (train/val/test). Real, Omicron-clean noise is close to zero-mean and
  stationary, so its statistics shouldn't meaningfully depend on overall
  sign — a roughly free 2x multiplier on usable noise diversity.
- **Time reversal**: applied to **train only**, not validation or test.
  Held back from val/test out of caution — while a roughly stationary
  noise floor should be close to time-symmetric, subtle secular drift
  within a segment could break that more than sign-symmetry does, and
  this hasn't been empirically verified. Not risking contamination of
  the metrics used to judge the model.

Signal and glitch augmentation via these same transforms were
deliberately **not** used:
- Sign-flipping an injected CBC signal is equivalent to shifting its
  coalescence phase by π — already fully covered by the existing
  uniform(0, 2π) phase prior, so it adds no new information.
- Time-reversing a CBC signal produces an unphysical "reverse chirp"
  (frequency decreasing toward a fake merger) that no real signal ever
  looks like; time-reversing a glitch corrupts the asymmetric time
  structure that makes glitches recognizable in the first place. Both
  would actively teach the network incorrect morphology.

## Signal injection: SNR sampling

Rather than drawing distance directly from `_random_cbc_parameters`'s
uniform-in-comoving-volume prior — which, since volume scales as d³,
concentrates the overwhelming majority of draws near `DMAX_MPC` and
produces mostly invisible signals — a target **network SNR** is drawn
**log-uniformly** and the already-whitened injected signal is rescaled to
hit it exactly. This is mathematically exact, not approximate: strain
amplitude is linear in 1/D_L, so SNR is linear in strain amplitude, and a
flat multiplicative rescale of the whitened output is equivalent to
having injected at the corresponding distance in the first place. Network
SNR is computed against each sample's own *matched real ASD* (verified
directly against bilby's default design-curve PSD, which is what
`ifo.meta_data["optimal_SNR"]` uses unless explicitly overridden — using
it unmodified would have made "target SNR" meaningless relative to the
real noise the signal is actually embedded in).

- `SNR_MIN = 5.0`, `SNR_MAX = 150.0` — deliberately spans below the
  conventional network SNR=8 confident-detection threshold (marginal
  examples matter) up to well past the loudest real O3/O4 events (~SNR
  20-30), so the network also sees loud, clean examples of true signal
  structure. Log-uniform(5, 150) puts ~12% of draws above SNR=100 and
  ~20% below SNR=10 — a present but minority loud tail, not the bulk of
  the distribution. (250 and 300 were considered and rejected as ceilings
  — 23-27% of draws would exceed SNR=100, a scale no real O3/O4 event has
  ever approached.)
- `NO_INJ_PROB = 0.02` — 2% of samples get no astrophysical signal
  injected at all, so the network sees genuine negative examples (real
  noise + glitch only). Lower than the simulated pipeline's 5%, since
  with SNR sampled directly rather than inherited from an uninformative
  distance prior, most injected signals are now meaningfully loud, so
  fewer explicit negatives are needed to balance the dataset.

## Duplication factor and final size

**10x duplication per sample**: each pooled (H1+L1) 8s sample contributes
10 generated training examples (or 10 for val, 10 for test — each split's
own pool duplicated independently at the same factor). Each of those 10
draws gets its own random sliding-window offset, its own sign-flip/
reversal decision, and an entirely fresh signal/glitch draw.

At the sample level this is 10x; at the level of genuinely independent
noise (contexts, not the 13-way-overlapping samples), it works out to
roughly **130x reuse per independent context** (13 samples/context × 10x
duplication). This is more aggressive than the sample-level number alone
suggests, but is judged acceptable given: fresh signal/glitch every draw
(not literal duplicate training examples), sliding-window + sign-flip +
(train-only) reversal adding real variation within that reuse, GPS-based
splitting guaranteeing zero context leakage between train/val/test, and
validation loss + early stopping providing a direct check against actual
memorization (which a disjoint-context validation set is well-positioned
to catch, even if it can't detect a representativeness blind spot shared
by train and val alike — the chronological test set exists partly to
probe that separately).

Resulting dataset size:

| | O3 | O4 |
|---|---|---|
| train | 109,210 samples (~40 GiB) | 444,350 samples (~163 GiB) |
| val | 13,650 samples (~5 GiB) | 55,540 samples (~20.3 GiB) |
| test | 13,650 samples (~5 GiB) | 55,540 samples (~20.3 GiB) |
| **total** | **~50 GiB** | **~203 GiB** |

Combined ≈ **253 GiB**, roughly a quarter of the 1TB Snellius storage
budget — well short of matching the simulated pipeline's ~945 GiB scale,
by design: real noise is a finite, fixed resource (bounded by how much
Omicron-clean O3/O4 time was fetched), unlike simulated noise which is
generated fresh on demand, so matching that scale would have required
reuse factors (~500-900x per independent context) judged too aggressive
relative to what real noise actually offers.

## Sequencing note

The existing simulated training dataset on Snellius is being kept until
the O3/O4 real-noise pipeline is generated, rsynced, and confirmed
training cleanly on both H100s — not deleted first. Given limited
remaining time on the compute allocation, losing a working baseline
before the replacement is confirmed working is the single highest-risk
mistake to avoid here.
